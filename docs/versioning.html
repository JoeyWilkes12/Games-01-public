Application versioning

How versions are chosen, what stays compatible, and what the history can establish.

The application uses Semantic Versioning 2.0.0 and a curated Keep a Changelog 1.1.0 changelog. version.json is the source of truth for the application version.

The current worktree is 3.4.0-alpha.5, the approved 3D-dice prerelease on codex/dice-3d-roll. The GitHub Pages source still uses the tagged mobile baseline 3.4.0-alpha.3 on codex/mobile-game-lab. The separate codex/library-design-system branch uses 3.4.0-alpha.4 and is not included in this preview. main remains at its existing baseline. The intended stable version is 3.4.0 because the work adds and reorganizes user-facing features while preserving saved-game configuration compatibility. A visual redesign alone does not require a major version.

What the version covers

The application's compatibility contract includes saved configuration formats, exported data formats, game rules, supported navigation URLs, and documented JavaScript integrations. Styling, navigation organization, and dashboard layout can evolve within that contract.

  • Increment PATCH for compatible bug fixes and small presentation corrections.
  • Increment MINOR for compatible new features, substantial interface improvements, or newly supported data.
  • Increment MAJOR for incompatible changes to the contract, such as removing a supported configuration format or changing an exported data schema without backward compatibility.
  • Use prereleases such as 3.4.0-alpha.1, 3.4.0-beta.1, and 3.4.0-rc.1 while the work is being validated. Increment the suffix when sharing a new preview.

Configuration version fields inside Bank, 2048, and Random Event Dice exports identify their own schema. They are independent of the application release and must not be rewritten to match the app version. Random Event Dice's existing 2.0 and 2.1 schemas are an example.

The root npm package originally identified the Playwright test harness as games-01-playwright@1.0.0. That historical package version does not establish an application release. If the package becomes the application's build manifest, synchronize it and its lockfile with version.json; until then, the shared JSON manifest identifies the app.

Displaying the version

The shared scripts/version.js loader reads version.json relative to its own URL and updates elements with the data-app-version attribute. Use a readable fallback so the page still identifies the preview if the manifest cannot load:

<span data-app-version>v3.4.0-alpha.5 · Preview</span>
<script src="scripts/version.js" defer></script>

Nested game pages can load the same script using their relative path, for example ../../../scripts/version.js. Do not keep separate game footer version constants. The manifest records status: "unreleased" for local-only work and status: "prerelease" for a published alpha, beta, or release candidate. Both carry the Preview label.

Maintaining the changelog

Write short descriptions of meaningful user-facing behavior in CHANGELOG.md under Unreleased. Use only applicable categories: Added, Changed, Deprecated, Removed, Fixed, and Security. Keep entries newest first and retain historical labels rather than quietly rewriting old release identities.

A release preparation should select its final SemVer, replace the Unreleased entries with a dated section, update the manifest and any synchronized package metadata, and verify the UI display and compatibility. Use the real release date, not a planned date. A release tag should reference the approved release commit; compare links should use real tags after those tags exist.

This policy does not authorize merging, publishing, deploying, or creating tags. Those actions require the project's separate authorization and release workflow.

Integrating the parallel work

The dice branch contains all four mobile-baseline commits. Its PR to main therefore includes the mobile redesign, shared themes, themed reading pages, and QR code as well as the dice changes. Merging a second mobile-baseline PR would not add distinct work after that PR lands.

The Library branch adds two commits after the same baseline. It can be integrated in a follow-up PR once the dice PR is reviewed and merged. If both features must ship together, use a temporary integration branch created from current main, review the feature PRs against that branch, resolve shared version/changelog/design files, test the combined app, and open one final integration PR to main. Every specific PR merge still requires the user's explicit approval; approval of a preview or permission to open a PR does not authorize merging it.
